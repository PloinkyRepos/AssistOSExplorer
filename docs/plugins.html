Plugins

Explorer plugins exist so the IDE shell can grow without turning every domain capability into hardcoded host logic. The host needs ways to surface Git actions, DPU tools, SOPLang operations, media affordances, and other contextual UI without rebuilding Explorer every time one agent adds a new interaction. A plugin is the unit that makes that possible: a browser-side WebSkel bundle with a manifest, assets, and a presenter that can be mounted into the Explorer UI at defined locations.

This matters architecturally because Explorer owns the shell, not the domain logic. Plugins are how domain agents project UI into that shell while keeping responsibility for their own tools and state. A plugin can open a modal, mount inline controls, or expose toolbar actions in context, but it does not change the underlying ownership rule: Explorer hosts the interaction surface, while the owning agent remains responsible for the domain operation behind it.

The important point is that Explorer does not treat “document plugins” and “application plugins” as unrelated systems. The same plugin mechanism covers both. What changes is the manifest metadata: pluginCategory declares whether the plugin belongs to the document-oriented runtime or the application shell, and location determines where it can mount. Document plugins use document locations such as document, chapter, paragraph, or infoText. Application plugins use application slots such as file-exp:toolbar. The runtime loader, presenter model, asset resolution, and manifest-driven discovery are otherwise shared.

Runtime Discovery

Explorer discovers plugins through aggregateIdePlugins in filesystem-http-server.mjs. When the browser calls collect_ide_plugins, Explorer scans enabled agent or repo-local plugin folders in the workspace for IDE-plugins/*/config.json, resolves their assets, groups them by location, and returns the merged catalog to the frontend. For application-category plugins, the browser then applies Explorer's applicationPlugins policy before mounting them.

That discovery model means plugin registration is driven by manifests, not by a central switch statement in the host. It also means plugin availability is a runtime property of the workspace: which agents are enabled, which plugin folders exist, and which application policies are active. Explorer stays in control of slot names and mounting behavior, but plugin presence itself comes from the workspace state rather than from a compile-time bundle list.

In the current repository, the discovered catalog includes both shell-mounted and document-mounted plugins. Shell examples include application plugins such as git-tool-button, tasks-tool-button, and open-builder-button, which mount into application slots like file-exp:toolbar. Document-oriented examples include video-plugin, audio-plugin, image-plugin, run-script, and edit-variables, which mount in document, chapter, paragraph, or info text contexts. The mechanism is shared; only the mounting regime and policy filters differ.

Manifest Contract

The plugin manifest in config.json is the contract between a plugin bundle and the Explorer host. It tells Explorer which component to load, which presenter to instantiate, what type of UI to mount, where that UI belongs, and which icon or tooltip to expose to the user. The host does not discover a plugin by reading its JavaScript entry point first; it discovers the manifest and uses that file as the runtime description of how the plugin should appear.

The most important structural fields are the same regardless of where the plugin mounts. Every plugin declares a pluginCategory, a component, a presenter, a type, and at least one location. For document-category plugins, location must be one of the supported document locations. For application-category plugins, location must be an application slot key such as file-exp:toolbar. Application plugins can also expose policy keys through id, which is how the Explorer applicationPlugins policy can enable or disable them at runtime.

A representative manifest from the video-creator plugin looks like this:

{
  "pluginCategory": "document",
  "component": "video-creator",
  "presenter": "VideoCreator",
  "type": "modal",
  "location": [
    "document"
  ],
  "tooltip": "Create a video from a script",
  "icon": "./assets/icons/video.svg"
}

In practice, this tells Explorer to load the video-creator bundle as a modal, mount it at the document level, and decorate the entry point with the declared tooltip and icon. An application plugin follows the same pattern, but with pluginCategory: "application" and a shell slot location such as file-exp:toolbar. The host-side discovery logic remains the same.

Authoring Example

The smallest useful authoring example is still a plugin that changes one paragraph through the existing document runtime, because it shows the full presenter lifecycle with minimal code. The point of the example is not the uppercase transformation itself; it is the shape of the plugin. A plugin folder lives inside the agent that owns the feature, carries its own config.json, HTML template, and presenter, and uses the host context plus the owning runtime APIs rather than trying to patch Explorer internals directly.

Create a new folder such as multimedia/IDE-plugins/uppercase/ or soplangAgent/IDE-plugins/uppercase/, then add the files below. If you were building an application plugin instead, the same structure would apply; you would mainly change pluginCategory and location so the bundle mounts into a shell slot rather than a document slot.

config.json

{
  "pluginCategory": "document",
  "component": "uppercase-plugin",
  "presenter": "UppercasePlugin",
  "type": "modal",
  "location": ["paragraph"],
  "tooltip": "Uppercase paragraph",
  "icon": "./icon.svg"
}

uppercase-plugin.html

<div class="modal-header">
  <div>Uppercase Paragraph</div>
  <div class="close" data-local-action="closeModal">×</div>
</div>
<div class="modal-body">
  <p>This will convert the paragraph with text: "<strong>${this.paragraph.text}</strong>" to uppercase.</p>
  <button class="general-button" data-local-action="apply">Apply</button>
</div>

uppercase-plugin.js

import { getContextualElement } from "../utils/pluginUtils.js";
const documentModule = assistOS.loadModule("document");

export class UppercasePlugin {
  constructor(element, invalidate) {
    this.element = element;
    this.invalidate = invalidate;
    this.invalidate();
  }

  beforeRender() {
    const { chapter, paragraph } = getContextualElement(this.element);
    this.chapter = chapter;
    this.paragraph = paragraph;
  }

  afterRender() {
    const button = this.element.querySelector('[data-local-action="apply"]');
    button.addEventListener("click", this.apply.bind(this));
  }

  async apply() {
    const text = this.paragraph?.text || "";
    await documentModule.updateParagraphText(this.chapter.id, this.paragraph.id, text.toUpperCase());
    assistOS.UI.showToast("Paragraph updated successfully!", "success");
    this.closeModal();
  }

  closeModal() {
    assistOS.UI.closeModal(this.element);
  }
}

This presenter shows the expected shape of a WebSkel-driven Explorer plugin: resolve context in beforeRender(), attach browser events in afterRender(), call into the existing document module for the real mutation, then close the modal through the host UI. That is the pattern to preserve when adding new plugins: the plugin owns its local interaction, but it still works through the host contracts and the owning runtime modules.
