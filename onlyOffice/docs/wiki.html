OnlyOffice Terminology

Explorer

Explorer is the AchillesIDE workspace shell that lets an authenticated user select an Office document and request an OnlyOffice editor session. It calls the authenticated control route and loads the returned browser configuration through the Router-exposed editor transport.

Explorer owns the ordinary workspace interaction but does not proxy DocumentServer traffic itself. The OnlyOffice agent validates the session and callback boundaries, while DPU remains authoritative for Confidential storage.

OnlyOffice integration

The OnlyOffice integration connects Explorer document previews to OnlyOffice DocumentServer under the Runtime-v5 routing contract. An authenticated Explorer request creates a bounded editor session, the public editor transport carries sanitized DocumentServer traffic, and the signed callback path persists the resulting document through the storage owner selected for that file.

The integration owns session state, token generation and validation, callback checks, forwarding validation, drain behavior, and storage selection. It does not make DocumentServer the owner of workspace files, expose direct host ports as the browser contract, or allow the public editor path to reuse Explorer credentials.

Runtime-v5

Runtime-v5 is the active OnlyOffice deployment contract. It separates authenticated control on Router target 7000, public editor transport on target 8080, and internal callback storage on target 9100. Ploinky starts the pinned image and supplies the generated secrets, persistent volumes, route access, and DPU delegation required by those services.

The runtime verifies exact nginx configuration, DocumentServer and support-service listeners, expected file copies and modes, process ownership, and callback storage before activation. Router targets identify container services; they do not create physical-host port publications.

Ploinky

Ploinky starts the OnlyOffice agent, supplies its runtime environment, installs the authenticated and public Router routes, and mediates verified invocation context. It also generates the shared OnlyOffice JWT secret and mints the scoped Confidential delegation when the authenticated control request requires DPU storage.

OnlyOffice derives browser-facing editor URLs from the Router-authenticated forwarded origin. A local listener address is an internal service detail and is not a substitute browser route.

Router

The Router is the Ploinky service that exposes the manifest-declared OnlyOffice targets, authenticates the control route, permits the narrow public editor route, and supplies the verified forwarded origin used to construct browser URLs. It also mints the Confidential delegation and invocation context consumed by the control service.

The Router does not make the editor target a general public proxy. OnlyOffice still validates the complete forwarding tuple and session contract before contacting DocumentServer, and direct loopback listeners remain internal runtime details.

Router forwarding tuple

The Router forwarding tuple is the exact combination of internal Host, forwarded host, forwarded protocol, and forwarded prefix accepted by the public editor proxy. The proxy compares each value with the active session topology and rejects missing, duplicated, malformed, unexpected, or caller-supplied forwarding fields before opening an HTTP or WebSocket connection to DocumentServer.

After validation, the proxy installs canonical forwarding headers and removes browser Authorization headers, cookies, and unrelated credentials. This turns the public editor target into a narrow DocumentServer transport rather than a general reverse proxy.

DocumentServer

DocumentServer is the OnlyOffice service that serves the browser editor, co-editing transport, and document-save callbacks. The integration supplies a session-specific document key, editor configuration, callback URL, and signed token. DocumentServer returns editing results through the verified callback contract.

DocumentServer does not own the workspace or Confidential document. The selected workspace or DPU storage implementation remains authoritative, and a callback is persisted only after its session token, claims, forwarding metadata, body size, and storage operation pass validation.

Callback storage service

The callback storage service is the loopback-only OnlyOffice listener on target 9100. It supplies session-authorized document bytes to DocumentServer and receives signed save callbacks without exposing that internal exchange as a public browser route.

The service validates the callback token, claims, document key, source URL, content type, and body limits before writing through the selected workspace or DPU store. It remains available during controlled drain so active editor sessions can finish persistence before DocumentServer stops.

DocumentServer support services

The pinned DocumentServer image uses PostgreSQL for service data, RabbitMQ and the Erlang Port Mapper Daemon for internal messaging, and optional Redis where enabled by the image configuration. These services are internal dependencies started and checked by the OnlyOffice runtime.

Runtime-v5 verifies their expected listeners, files, addresses, modes, and process ownership. They are not public documentation endpoints, browser routes, or owners of the edited workspace document.

JSON Web Token

A JSON Web Token (JWT) signs the editor configuration and callback exchange for one OnlyOffice session. Configuration tokens have a positive lifetime no greater than five minutes and enter DocumentServer as the single signed top-level body token. Callback processing authenticates its own string token before using claims.

A token from another session cannot authorize the opaque callback URL even when both sessions refer to the same document. Tokens do not carry a DPU delegation bearer, and unsigned duplicate values must exactly match the verified non-temporal claims.

Topology generation

A topology generation is the immutable Router and service mapping selected when an editor session is created. Session state records the generation so editor transport, callback URLs, and restart handling continue to refer to one verified service layout.

During controlled replacement, OnlyOffice drains and persists active sessions and reopens service only after the new generation passes readiness checks. A session cannot silently switch to an unverified listener or forwarding prefix.

DocumentServer auto-assembly

DocumentServer auto-assembly periodically asks an open editor to produce a save state so callback-backed persistence does not depend only on the final editor close. The OnlyOffice manifest exposes the enabled flag, interval, and step consumed by the pinned DocumentServer image.

Auto-assembly does not bypass session authorization, callback JWT validation, body limits, source URL checks, or the selected storage policy. Its output follows the same callback storage path as another accepted save result.

DPU

DPU is the product identifier used by dpuAgent, the server-side authority for Confidential objects and their access policy. The repository does not define a longer expansion for the identifier. OnlyOffice calls the declared DPU tools only when the authenticated control request carries the Router-minted Confidential delegation.

DPU remains the storage and authorization owner for a protected document. OnlyOffice manages the editor session and callback validation but cannot replace DPU checks with direct filesystem access or a browser-supplied identity.

Confidential persistence delegation

The dpuConfidential delegation is a short-lived Router-minted grant that lets OnlyOffice call the specific DPU tools declared by the manifest for one authenticated Confidential workflow. It carries the approved audience, scopes, and tool restrictions used by dpuAgent to authorize document listing, reads, and writes.

The delegation remains outside persisted session state and browser configuration. A Confidential session without a valid delegation fails instead of falling back to direct workspace or host filesystem access.

AchillesAgentLib

AchillesAgentLib is the shared agent runtime library governed by the repository's agent coding rules. OnlyOffice may use a runtime-supplied library integration, but its product contract defines no model-driven editor behavior.

If OnlyOffice introduces an LLM interaction, the coding contract requires the configured LLMAgent class, environment-based model configuration, and repository-level manual overrides. Such an interaction cannot bypass the existing session, forwarding, callback, or storage boundaries.

Large language model

A large language model (LLM) is a model service that an agent could call through the repository's approved AchillesAgentLib integration. The OnlyOffice product contract does not use an LLM to create sessions, proxy editor traffic, validate callbacks, or persist documents.

The term appears only in the coding constraint that governs any later model interaction. It does not describe an active OnlyOffice editor dependency or a participant in the Runtime-v5 architecture.
